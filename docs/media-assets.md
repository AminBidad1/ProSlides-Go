# Media assets

Status: active implementation contract  
Last reviewed: 2026-09-30

## Purpose

ProSlides has one image-media system. Media is a bounded context inside the
existing Go modular monolith. PostgreSQL stores immutable asset/rendition
metadata and object storage holds the binary bytes.

A Media Asset represents image content only. It does not mean "background",
"question image", "answer image", "Word Cloud image" or "Content image".
Those meanings belong to authoring placement data in the presentations domain.

This separation is deliberate:

```text
Media Asset (immutable content)
       |
       +-- Background placement
       +-- Question prompt placement
       +-- Answer-option placement
       +-- Word Cloud prompt placement
       `-- Content placement
```

One asset may therefore be reused by many placements and many Presentations
without copying the binary.

## Core rules

1. Uploaded assets are immutable. Replacing an image creates or selects another
   asset; editing placement never rewrites the asset.
2. The media domain owns image validation, normalization, object writes,
   rendition generation and immutable delivery.
3. The presentations domain owns how an asset is used: fit, focal point,
   accessibility text and slot-specific layout.
4. Production binaries never live in PostgreSQL or the API container
   filesystem.
5. Provider URLs and credentials are never product truth. Persisted references
   use an opaque Media Asset UUID plus stable first-party delivery paths.
6. The browser may downscale/re-encode before upload for UX and bandwidth, but
   browser processing is never a security boundary. The Go API independently
   decodes and validates every upload.
7. Responsive renditions are generated by the trusted Go media service from
   the accepted master. The browser cannot submit a thumbnail/variant for a
   different image.
8. Renditions never upscale. A 320 px source does not produce fake 480/1280/
   2560 px copies.
9. Reuse and SHA-256 deduplication are scoped to the same owner. Cross-account
   deduplication is intentionally avoided.
10. Public delivery is immutable and cacheable; the private object-store key,
    credentials and owner metadata are never exposed.
11. A media failure must degrade the visual surface safely and must never break
    live navigation, scoring or Session state.

## Storage topology

```text
Author browser
    |
    | authenticated upload
    v
Go API / media bounded context
    |---- PostgreSQL: media_assets + media_variants metadata
    `---- private object storage
           |-- local filesystem in development
           `-- Cloudflare R2 in production

Viewer browser
    |
    | first-party immutable URL
    v
/api/v1/media/assets/{id}/...
    |
    `---- object adapter -> cache/CDN when configured
```

No separate media application server or microservice is introduced.

The current production adapter uses Cloudflare R2's REST object API with a
server-side token. The media domain depends only on `ObjectStore`; switching
to the S3-compatible adapter or another object store must not change
presentation data.

## Input policy

Accepted author input:

- JPEG/JPG;
- PNG.

Current limits:

- maximum request image bytes: 15 MiB;
- maximum decoded pixels: 16 megapixels;
- maximum dimension: 8192 px on either axis.

The official web client caps the master long edge at 3840 px before upload and
re-encodes it. PNG transparency is preserved; JPEG uses the current matte
background when browser preprocessing needs an opaque surface. The server then
decodes and re-encodes the file again, strips embedded metadata and applies the
authoritative limits.

SVG, animated GIF, HEIC and arbitrary binary uploads remain intentionally
unsupported until their decode/sanitize contracts are designed explicitly.

## Master and renditions

The accepted normalized master is immutable. The backend may additionally
create these standard renditions from the same decoded source:

| Rendition | Maximum long edge | Typical use |
|---|---:|---|
| `thumbnail` | 480 px | media library, compact previews |
| `medium` | 1280 px | participant/mobile and moderate editor slots |
| `large` | 2560 px | Stage/manager/projector content images |

A rendition is omitted when the source is already at or below that size. This
prevents upscaling and unnecessary storage.

Rendition metadata lives in `media_variants`, not as fixed columns on
`media_assets`. Adding a future rendition class therefore does not require
turning the asset row into an ever-growing list of context-specific columns.

## Database contract

`media_assets` stores the immutable master metadata:

- UUID;
- owner;
- generic purpose (`image`);
- private master object key;
- MIME type;
- width and height;
- byte size;
- normalized SHA-256;
- processing / ready / failed status;
- original display filename;
- timestamps.

`media_variants` stores zero or more immutable derived renditions:

- asset ID;
- rendition name;
- private object key;
- MIME type;
- width/height;
- byte size;
- creation time.

Asset metadata and rendition metadata are inserted in one PostgreSQL
transaction. Object writes happen only after metadata creation. If an object
write fails, written objects are best-effort cleaned up and the asset is marked
failed so a partial asset can never be served as ready.

The owner foreign key is restrictive. Account deletion must explicitly
reconcile media and object storage before the user record can be removed.

## HTTP contract

### Author library

`GET /api/v1/media/images`

- authenticated account session required;
- owner-scoped ready assets only;
- newest-first opaque cursor pagination;
- bounded page size;
- returns public delivery metadata, never private storage keys.

### Upload

`POST /api/v1/media/images`

- authenticated account + CSRF required;
- one multipart `file`;
- server validates and normalizes the master;
- server generates standard renditions;
- same-owner duplicate normalized bytes reuse the existing ready asset;
- response returns the immutable asset manifest.

The API intentionally does not accept browser-generated rendition fields.

### Delivery

`GET /api/v1/media/assets/{assetId}/content`

returns the normalized master.

`GET /api/v1/media/assets/{assetId}/renditions/{variant}`

returns an existing `thumbnail`, `medium` or `large` rendition. Missing
renditions return 404; clients must choose a rendition based on known asset
metadata or fall back to the master.

All successful delivery responses use:

```text
Cache-Control: public, max-age=31536000, immutable
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Cross-Origin-Resource-Policy: same-origin
```

## Placement contract

Asset identity and image placement are different data.

Background placement persists its existing theme-specific placement:
an immutable asset ID for first-party media, a compatibility delivery URL,
normalized focal x/y coordinates and cover rendering.

Question prompts, answer options, Word Cloud prompts and Content images use the
shared Presentation image-placement contract. The wire representation keeps
`image_url` for compatibility and may additionally carry
`image_asset_id`, intrinsic `image_width`/`image_height`,
`image_alt_text` and normalized `image_focal_x`/`image_focal_y`.

For first-party media, the Go API treats the asset ID as the authority. It
verifies that the ready image belongs to the authenticated owner and
canonicalizes the delivery URL and intrinsic dimensions before persistence.
A client cannot claim another owner's asset or make submitted dimensions
authoritative. External HTTP(S) URLs remain supported without an asset ID for
legacy authoring compatibility.

The Editor has one `ImagePlacement` model across these non-background slots.
Drafting, validation, previews and serialization preserve asset identity instead
of collapsing a reusable asset back into a URL. All slots use the same media
picker for upload/reuse, with the external-URL path kept as a secondary
compatibility action. Preview surfaces request an appropriate rendition for first-party media and
fall back once to the immutable master when a historical asset does not have
that rendition. Missing variants therefore do not turn an otherwise valid
legacy asset into a broken editor preview.

Stored legacy definitions remain readable even when an old image URL would no
longer be accepted for a new authoring write. New writes apply the current URL
and first-party asset rules. This read/write distinction is intentional
migration compatibility, not a second authoring model.

A placement change must never create a new Media Asset.

## Live-session behavior

Session creation freezes authored Presentation/Item definitions. Therefore the
asset reference and placement metadata used by a Session must remain stable
even if the editable Presentation is changed later.

Background images remain projection-only on Stage/manager; participant surfaces
keep the derived image-free theme. Non-background content images follow their
own slot contract and may be delivered to participants when they are part of
the activity/content itself.

## Failure semantics

- corrupt or unsupported image -> 400 `invalid_image`;
- upload over limit -> 413 `media_too_large`;
- excessive dimensions -> 400 `image_dimensions_invalid`;
- object-store failure -> 503 `media_storage_unavailable`;
- unknown/non-ready asset -> 404;
- unknown/non-generated rendition -> 404;
- failed upload never updates an authoring placement;
- ready asset bytes never mutate.

## Lifecycle

Removing an image from a Presentation removes only that placement reference.
The Editor deliberately does not expose destructive asset deletion yet.

Hard deletion and orphan garbage collection remain deferred until reference
accounting covers both mutable Presentations and frozen Sessions. A historical
Session is a real reference and must prevent premature object deletion.

## Deliberately deferred

- reference-counted/orphan garbage collection;
- asset deletion UI;
- search/collections/tags until real library size justifies them;
- direct browser-to-object-store uploads;
- extra input formats;
- a media microservice.

The goal is one small, coherent image subsystem, not a collection of image
features that happen to share a bucket.
